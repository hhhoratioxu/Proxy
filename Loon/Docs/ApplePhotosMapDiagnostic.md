# Apple 照片地图诊断 0.2.0

目标是让中国大陆拍摄的照片使用对应的国内地图数据，境外照片使用对应的国际地图数据，切换依据应当是地图所展示的地点。当前交付的是排查所需的诊断插件，**自动分源与定位修复尚未实现**。不要把日志中的命中当成照片位置已经修复。

## 安装和提供诊断

要求 Loon **3.5.1 (983)** 或更新版本。将下方地址添加到 Loon 的远程插件中并启用；确认 Loon 的 HTTPS 解密和已经安装、信任的 MitM 证书可用。

```text
https://raw.githubusercontent.com/hhhoratioxu/Proxy/codex/apple-photos-map-diagnostics/Loon/script/ApplePhotosMapDiagnostic.lpx
```

1. 打开“照片”，找一张位置原本正确的中国大陆照片，上滑打开地点小地图，再点开地图并放大。
2. 在 Loon 的脚本日志中复制这一时段以 `[ApplePhotosMapDiagnostic]` 开头的内容。
3. 对一张偏移的境外照片重复同样操作，分别标明“国内照片”和“境外照片”；附上 iOS 版本、实际拍摄国家或地区、偏移大约几百米还是另一个城市。
4. 诊断完成后停用本插件。

**只需分享本插件输出的摘要行**，无需发送照片、完整网络记录、抓包文件或整条请求 URL。Loon 的其他网络日志可能包含坐标和令牌，本插件不控制那些日志。若插件没有输出，先查看所打开页面是否使用了缓存，以及对应 HTTPS 请求是否完成解密；不要反复修改照片的位置，也不需要清空照片图库或改动系统定位。

如果其他地图脚本已启用，Loon 每次请求/响应只执行第一条完整命中的 Script，诊断可能没有机会运行。可先记录当前状态，在这次短时排查时停用冲突的地图脚本，结束后恢复。用户已提供 Loon 3.5.3 (1008) 中 0.1.0 的 REQUEST 成功执行记录；0.2.0 请求头识别、响应日志和位置修复均尚未实机验收。

`.lpx` 是本项目当前的安装入口；此前的 `.plugin` 链接保留相同内容以兼容已导入的订阅，二者选择一个即可。

## 能观察什么

脚本仅匹配配置中明确列出的 Apple 地图资源清单、单个地图瓦片与两种地点调度接口。请求阶段读取 URL 中已知参数的**名称**；对于瓦片请求，还检查四个公开研究中观察到的请求头 `maps-tile-x/y/z` 和 `maps-tile-style`。坐标只在脚本内部做整数、缩放级别和网格范围校验，日志仅输出是否有效、参数载体、缩放级别以及样式、比例、尺寸等有限整数。请求头名称比较不区分大小写，重复、冲突、超限和不完整的坐标不被当成可用坐标。

响应阶段仅解析不超过 1 MiB 的成功资源清单，输出瓦片总数、国内/国际服务器数量和位置转换服务类别；资源清单的 304/错误状态、瓦片和地点调度响应只观察状态及受限内容类型，不读取正文。HTTP GET 没有 URL 参数本身不构成报错，坐标可能通过请求头传递。

未知参数只计数，URL、经纬度、瓦片 x/y、照片标识、账户、令牌、Cookie、原始请求头和正文均不输出。脚本不读取鉴权头、Cookie、`x-tilekey` 或其他未知请求头的值。单次最多枚举 128 个请求头；样式头不超过 2,048 个字符，参数扫描最多 128 项。所有路径通过 `$done({})` 保留原请求/响应。没有脚本网络请求、持久缓存、定时任务或外部收集服务器；实际地图流量仍由原请求发送给原服务商。

新日志中 `tile.carrier = "headers"` 且 `tile.coordinates = "valid"` 只说明从请求头识别到了合法瓦片坐标；`carrier = "query"` 表示从 URL 参数识别；`coordinates = "conflict"` 表示两处不一致。它们不证明照片标记已正确对齐，也不判定照片拍摄国家。顶层 `provider = "apple-cn"` 仅分类实际请求端点，不表示该照片一定拍于中国大陆。

这些接口可能由其他使用 MapKit 的应用共用，Loon 的这些规则无法验证调用者一定是“照片”。请分别打开两张照片，靠操作时间区分日志。未知协议、超过范围的域名与路径不捕获；批量瓦片、HTTP/3/未能解密的流量、系统本地转换以及缓存地图可能不可见。

## 当前证据与未完成部分

2026-10-19 已在桌面直接取得 Apple 返回的国内版与国际版资源清单。测试请求中的 `country_code=US` 与 `country_code=CN` 对 iOS 返回的数据源相同，JP 请求返回的瓦片端点不同。因此，只改地区参数无法证明拿到了正确的底图，也无法证明照片坐标转换正确。此观察限于当时使用的测试参数与网络，并非所有 iPhone 的结论。

此前尝试构造单瓦片请求时得到 HTTP 403/500。2026-10-20 用户提供的 0.1.0 日志确认，Loon 3.5.3 (1008) 捕获到无查询参数的 GET `/tiles`，脚本完成，端点被分类为 `apple-cn`。这份记录没有说明它来自哪张照片、iOS 版本、原始请求头、响应状态或偏移距离，无法据此判定根因。0.2.0 因此补充只读请求头识别与瓦片响应状态；不是把这份空查询记录当成协议故障。

还需要目标 iPhone 的新版摘要及症状，判断下一步应处理底图选择、地点解析还是本地显示转换。如果问题发生在系统本地转换或已写错的照片元数据，仅修改网络请求未必能解决。

0.1.0 的 34 项历史本地检查包含四份真实 Apple 资源清单。0.2.0 共 55 项本地检查通过，覆盖公开请求头格式、坐标和令牌不进入日志、参数冲突、失败退回、畸形输入、连续调用和实际导入文件的匹配范围。没有运行 Loon 原生配置解析器；用户的旧版 REQUEST 日志不替代新版请求头识别与位置验收。
